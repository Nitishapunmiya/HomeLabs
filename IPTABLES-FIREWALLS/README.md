# Mini Firewall + Splunk SOC Lab — Architecture

## 1. Project Overview

This project is a hands-on cybersecurity lab designed to demonstrate how a Linux-based firewall can be used to control network traffic, generate security logs, and forward those logs to a SIEM for centralized monitoring.

The lab combines:

* Kali Linux
* WSL Ubuntu
* `iptables`
* `rsyslog`
* `conntrack`
* Splunk Universal Forwarder
* Splunk Enterprise
* Nmap
* Netcat
* curl

The project focuses on the relationship between **network traffic, firewall enforcement, security logging, and SIEM-based investigation**.

---

## 2. Lab Architecture

The lab consists of three primary systems:

| System        | Role                                   |
| ------------- | -------------------------------------- |
| WSL Ubuntu    | Traffic generation and testing         |
| Kali Linux VM | Protected host and `iptables` firewall |
| Windows Host  | Splunk Enterprise / SIEM               |

Kali Linux acts as the main security enforcement point.

WSL Ubuntu is used to generate controlled network traffic toward Kali, while Splunk Enterprise receives and analyzes the resulting firewall events.

---

## 3. Network Architecture

Kali Linux uses multiple network interfaces for different purposes.

### NAT Network

The NAT interface provides Kali with external network connectivity.

### Host-Only Network

The Host-Only interface provides an isolated communication path for the lab systems.

The Host-Only network was used for controlled traffic testing between WSL Ubuntu and Kali.

Example lab addressing:

```text
WSL Ubuntu
192.168.56.1
      │
      │ Host-Only Network
      │
      ▼
Kali Linux
192.168.56.102
```

Kali also has a separate NAT-side address used for external connectivity.

---

## 4. Security Architecture

Kali Linux is the main security enforcement system.

Incoming traffic is evaluated by `iptables`.

Depending on the configured rules, traffic can be:

* Accepted
* Dropped
* Logged

Blocked traffic can generate a firewall log event using a custom logging prefix.

```text
Incoming Traffic
       ↓
   iptables
       ↓
 ┌─────┴─────┐
 │           │
ACCEPT      DROP
             │
             ▼
            LOG
```

---

## 5. Logging Architecture

Firewall events generated by `iptables` are handled through the Linux logging system.

The basic logging path is:

```text
iptables LOG
     ↓
Linux Kernel
     ↓
rsyslog
     ↓
/var/log/kern.log
```

A custom prefix such as:

```text
IPTABLES-BLOCK
```

is used to make firewall-generated events easier to identify.

The resulting log entries contain network information such as the source IP, destination IP, protocol, and destination port.

---

## 6. SIEM Architecture

The firewall log is forwarded from Kali to Splunk Enterprise.

The forwarding architecture is:

```text
Kali
/var/log/kern.log
       ↓
Splunk Universal Forwarder
       ↓
TCP/9997
       ↓
Splunk Enterprise
```

The Universal Forwarder is responsible for collecting the log file and forwarding events to the Splunk receiving service.

Splunk Enterprise provides the centralized environment for searching and investigating the collected firewall events.

---

## 7. Connection Tracking

The Linux connection-tracking subsystem is used to observe network sessions.

`conntrack` provides visibility into connection states such as:

```text
NEW
SYN_SENT
SYN_RECV
ESTABLISHED
FIN_WAIT
LAST_ACK
TIME_WAIT
```

This provides additional visibility into how network connections are created, maintained, and terminated.

---

## 8. Traffic Testing

Controlled traffic is generated from WSL Ubuntu and other lab components.

The following tools are used for different testing purposes:

| Tool      | Purpose                                   |
| --------- | ----------------------------------------- |
| Netcat    | Test TCP connectivity                     |
| curl      | Test HTTP connectivity                    |
| SSH       | Test remote administration connectivity   |
| Nmap      | Perform controlled network reconnaissance |
| conntrack | Observe connection states                 |

The generated traffic allows the firewall rules and logging pipeline to be validated.

---

## 9. Overall Security Workflow

The overall architecture can be summarized as:

```text
Traffic Generation
       ↓
Kali Linux
       ↓
iptables Firewall
       ↓
Firewall Decision
       ↓
Firewall Logging
       ↓
kern.log
       ↓
Splunk Universal Forwarder
       ↓
Splunk Enterprise
       ↓
Security Investigation
```

---

## 10. Project Scope

The current project demonstrates:

* Linux firewall administration
* Network traffic filtering
* Port-based access control
* SSH protection
* Firewall logging
* Linux connection tracking
* Centralized log collection
* SIEM-based log investigation
* Network reconnaissance and traffic testing

The project currently focuses on **firewall prevention, logging, collection, and investigation**.

Automated behavioral detection and automated IP blocking are outside the current implementation and are considered future enhancements.

---

## 11. Project Outcome

The lab demonstrates how an individual firewall event can be followed through multiple security layers:

**Network Traffic → Firewall → Log → Log Forwarder → SIEM → Investigation**

This provides practical exposure to both **network security controls** and **SOC monitoring workflows**.
