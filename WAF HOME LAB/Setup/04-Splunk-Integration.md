# 04 — Splunk Integration

## 1. Overview

This stage integrates the **Web Application Firewall (WAF)** with **Splunk** so that security events generated by the WAF can be collected, searched, analyzed, and visualized.

The WAF in this lab runs on the Ubuntu server hosting:

* Apache2
* DVWA
* ModSecurity
* OWASP Core Rule Set (CRS)

ModSecurity generates security-related events in its audit log. These logs are forwarded to Splunk using the **Splunk Universal Forwarder**.


# 2. Why Integrate the WAF with Splunk?

Looking at WAF logs directly from the Ubuntu server is useful for troubleshooting, but it is not ideal for security monitoring.

Splunk provides a centralized location where WAF events can be:

* Searched
* Filtered
* Correlated
* Investigated
* Visualized
* Used to create detections
* Used to build security dashboards

This allows the project to move from:

```text
WAF Protection
```

to:

```text
WAF + Security Monitoring + Investigation
```

# 6. Splunk Components

This lab uses two important Splunk components.

## Splunk Server

The Splunk server receives and indexes the logs.

It is responsible for:

* Indexing events
* Searching events
* Running SPL queries
* Creating visualizations
* Building dashboards

## Splunk Universal Forwarder

The Universal Forwarder runs on the machine where the logs are generated.

In this lab, it is used to collect the WAF logs from the kali server and forward them to Splunk.


---

# 7. Install Splunk Universal Forwarder

The Universal Forwarder must be installed on the Ubuntu WAF server.

After installation, verify the Splunk Forwarder directory.

The standard installation location is:

```text
/opt/splunkforwarder/
```

Check:

```bash
ls /opt/splunkforwarder/
```

The Splunk Forwarder binary can be accessed using:

```bash
/opt/splunkforwarder/bin/splunk
```

---

# 8. Start the Universal Forwarder

Start the forwarder:

```bash
sudo /opt/splunkforwarder/bin/splunk start
```

Check its status:

```bash
sudo /opt/splunkforwarder/bin/splunk status
```

The forwarder should report that it is running.

---

# 9. Configure the Splunk Receiver

The Universal Forwarder needs to know where to send the collected events.

The Splunk server must therefore have a receiving port configured.

The commonly used Splunk receiving port is:

```text
9997
```

On the Splunk server, enable the receiving port through:

```text
Settings
   |
   v
Forwarding and receiving
   |
   v
Configure receiving
   |
   v
New Receiving Port
   |
   v
9997
```

The receiver listens for events sent by Splunk Universal Forwarders.

---

# 10. Configure the Forwarder Destination

On the Ubuntu WAF server, configure the Universal Forwarder to send events to the Splunk server.

The general command is:

```bash
sudo /opt/splunkforwarder/bin/splunk add forward-server <SPLUNK_SERVER_IP>:9997
```

Replace:

```text
<SPLUNK_SERVER_IP>
```

with the IP address of the Splunk server.

Verify the configured forwarding destination:

```bash
sudo /opt/splunkforwarder/bin/splunk list forward-server
```

The Splunk server should appear as an active forwarding destination.

---

# 11. Configure WAF Log Monitoring

The Universal Forwarder needs to be configured to monitor the ModSecurity audit log.

The log to monitor is:

```text
/var/log/apache2/modsec_audit.log
```

Add the file as a monitored input:

```bash
sudo /opt/splunkforwarder/bin/splunk add monitor \
/var/log/apache2/modsec_audit.log
```

This tells the Universal Forwarder:

```text
Monitor this file
       |
       v
Read new events
       |
       v
Forward them to Splunk
```

---

# 16. Verify Events in Splunk

Open the Splunk Web interface.

Navigate to:

```text
Search & Reporting
```

Search for the WAF log source.

A basic search can be:

```spl
index=* "modsec"
```

If the events contain identifiable ModSecurity fields or strings, this can help locate the WAF events.

Another useful starting search is:

```spl
index=* sourcetype=*
```

Then narrow the results based on the actual source and sourcetype assigned to the forwarded events.

---

# 17. Identify the WAF Log Source

When the first events arrive in Splunk, inspect the event metadata.

Important fields include:

```text
host
source
sourcetype
index
```

For example:

```text
host       = Ubuntu-WAF
source     = /var/log/apache2/modsec_audit.log
sourcetype = ...
index      = ...
```

The exact values depend on the Splunk input configuration.

These fields are important because they allow us to create precise searches instead of searching the entire Splunk dataset.

---

# 18. Search WAF Events

Once the events are visible in Splunk, search for ModSecurity-related activity.

Example:

```spl
index=* source="/var/log/apache2/modsec_audit.log"
```

A broader search can be:

```spl
index=* "ModSecurity"
```

Searches can then be refined based on:

* Source IP
* Requested URI
* HTTP method
* Rule ID
* Attack category
* Response status
* Host
* Timestamp

---

# 19. Finding Client IP Addresses

One of the most important pieces of information during WAF investigation is the source IP.

A search can be used to identify client IP information:

```spl
index=* source="/var/log/apache2/modsec_audit.log"
```

Then inspect the returned events for fields such as:

```text
client_ip
src_ip
remote_addr
```

The exact field name depends on how the ModSecurity audit log is parsed by Splunk.

The investigation goal is to determine:

```text
Who sent the request?
```

---

# 20. Finding Requested URLs

The requested URI is another important investigation artifact.

Search the WAF events and inspect fields related to:

```text
request
uri
url
path
```

This helps answer:

```text
What did the attacker try to access?
```

For example, an investigation may reveal:

```text
/api/login
/dvwa/vulnerabilities/sqli/
```

The exact URI depends on the attack performed.

---

# 21. Finding ModSecurity Rule IDs

ModSecurity and OWASP CRS events can contain rule IDs.

Search for rule-related information:

```spl
index=* source="/var/log/apache2/modsec_audit.log"
```

Then inspect the event for fields or text containing:

```text
id
rule
Matched
ModSecurity
```

A rule ID is important because it helps identify **which security rule detected the request**.

The investigation chain becomes:

```text
Source IP
    |
    v
Requested URI
    |
    v
Attack Payload
    |
    v
CRS Rule ID
    |
    v
WAF Action
```

---

# 22. Searching for SQL Injection

During the SQL Injection attack simulation, search for terms associated with SQL injection.

Example:

```spl
index=* source="/var/log/apache2/modsec_audit.log"
("SQL" OR "SQLi" OR "942")
```

This search is useful as an initial investigation query.

The exact rule ID and event content should always be confirmed from the actual WAF event rather than assumed.

---

# 23. Searching for XSS

During the XSS attack simulation, search for XSS-related events:

```spl
index=* source="/var/log/apache2/modsec_audit.log"
("XSS" OR "941")
```

This helps identify events generated by CRS rules associated with application-level XSS detection.

Again, the exact rule triggered should be confirmed from the actual event.

---

# 24. Searching for Command Injection

During the command injection simulation:

```spl
index=* source="/var/log/apache2/modsec_audit.log"
("command" OR "cmd" OR "932")
```

This can be used as an initial search for command-injection-related activity.

The actual detection should be validated against the ModSecurity event and the corresponding CRS rule.

# 25. Investigating a WAF Event

A typical WAF investigation should answer the following questions:

### 1. When did it happen?

Check:

```text
_time
```

### 2. Who generated the request?

Identify:

```text
Source IP
```

### 3. What was targeted?

Identify:

```text
Requested URI
```

### 4. What was sent?

Inspect:

```text
HTTP request
Payload
Headers
Parameters
```

### 5. Which rule detected it?

Identify:

```text
ModSecurity / CRS Rule ID
```

### 6. What happened to the request?

Determine whether it was:

```text
Allowed
Blocked
Rejected
```

### 7. What happened afterward?

Correlate the WAF event with other logs and investigate whether the attacker continued.

The investigation workflow is:

```text

                    |
                    v
             Identify Source IP

                    |

                    |
```

This approach helps turn a raw WAF event into an actionable security finding.

# 27. Basic SPL Queries

## View ModSecurity Events

```spl
index=* source="/var/log/apache2/modsec_audit.log"
```

## Search Recent WAF Events

```spl
index=* source="/var/log/apache2/modsec_audit.log"
| sort - _time
```

## Count Events by Source IP

```spl
index=* source="/var/log/apache2/modsec_audit.log"
| stats count by src_ip
| sort - count
```

If `src_ip` is not automatically extracted, inspect the raw event and identify the correct field.

## Count Events by Host

```spl
index=* source="/var/log/apache2/modsec_audit.log"
| stats count by host
```

## Count Events Over Time

```spl
index=* source="/var/log/apache2/modsec_audit.log"
| timechart count
```

## Search for ModSecurity

```spl
index=* "ModSecurity"
```

If the attack category is extracted into a field:

```spl
index=* source="/var/log/apache2/modsec_audit.log"
| stats count by attack_type
```

The exact field names depend on the parsing configuration.

# 29. Why Field Extraction Matters

Raw ModSecurity audit logs can be difficult to investigate because a single transaction contains multiple sections.

Splunk becomes much more useful when important values are extracted into fields.

Useful fields include:

```text
_time
src_ip
host
uri
http_method
rule_id
attack_type
status
user_agent
```

This allows searches such as:

```spl
index=* rule_id=941*
```

or:

```spl
index=* src_ip="ATTACKER_IP"
```

or:

```spl
index=* attack_type="XSS"
```

The exact syntax depends on the fields available in the indexed events.
